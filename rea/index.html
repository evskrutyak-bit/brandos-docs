01 / TL;DR

Понять суть за 30 секунд

Что это
Инструментальный слой для AI-агента

REA даёт агенту доступ к средствам анализа сайтов, приложений и бинарников.

Зачем
Чтобы исследовать, а не додумывать

Вместо «сделай как X» агент получает наблюдения, псевдокод, связи и ограничения.

Когда нужен
Когда поведение важнее внешнего вида

Закрытый SaaS, desktop-приложение, сложная механика, legacy-система без исходников.

Не «волшебная кнопка клонирования», а исследовательский контур: наблюдение → доказательства → вывод → собственная реализация. Official Официальный REA описывает себя как MCP для исследования приложений и бинарников без исходного кода, с локальным анализом, evidence и limitations.

03 / ЧТО ЭТО

REA не заменяет Codex. Он расширяет его органы чувств.

Agent

Думает и принимает решения

Codex или Claude Code формулирует гипотезы, выбирает следующий шаг, интерпретирует результаты и пишет новую реализацию.

REA

Оркестрирует исследование

Даёт агенту единый путь к инструментам анализа и возвращает результаты вместе с evidence и ограничениями.

Providers

Добывают технические факты

Для нативного анализа используются специализированные средства вроде Ghidra, Hopper или IDA; для web/JS есть другие режимы.

Official По текущему README REA подключает агента к анализу native binaries, JavaScript/Electron, .NET и websites; анализ выполняется локально.

Что здесь делает MCP?

MCP — стандартный способ подключать AI-приложения к внешним инструментам, ресурсам и данным. В этой схеме он служит мостом: coding agent получает возможность вызывать REA как внешний инструмент, а REA уже управляет специализированными средствами исследования.

Почему не дать агенту просто Ghidra?

Можно, но тогда вам придётся самостоятельно продумывать интеграцию и рабочий процесс. Ценность REA именно в унификации: одна точка входа, workflow для агента, доказательства и явные ограничения выводов.

05 / БЕЗ МАГИИ

Что REA делает и чего от него не надо ждать

REA делает
  • помогает исследовать поведение приложения
  • даёт агенту доступ к инструментам анализа
  • собирает технические наблюдения и связи
  • возвращает evidence и limitations
  • помогает построить совместимую собственную реализацию
REA не делает
  • не восстанавливает гарантированно исходный код
  • не превращает закрытый продукт в open-source
  • не гарантирует правильность каждой гипотезы AI
  • не отменяет тестирование результата
  • не делает любой сценарий использования правомерным

Official README отдельно указывает: декомпилятор не может гарантировать восстановление оригинального исходника; агент работает с псевдокодом, assembly, symbols, strings, metadata и relationships.

Есть исходный код

Дайте репозиторий coding agent

Скриншот + Figma + agent

Есть хорошая документация

11 / WORKFLOW

Правильный процесс работы с REA

01
Сузить объект исследования

Не «разбери Notion», а «разбери поведение database filters при нескольких условиях».

02
Сформулировать вопросы

Что именно нужно узнать: состояния, ошибки, branching, keyboard UX, формат данных, сетевые вызовы, внутренние связи.

03
Сначала получить research report

Попросить агента ничего не реализовывать, пока не отделены OBSERVED / INFERRED / UNKNOWN.

04
Проверить доказательства

Сопоставить выводы с тем, что реально наблюдалось или было найдено инструментами анализа.

05
Сформировать собственное ТЗ

Не копировать продукт целиком. Выбрать нужное поведение и адаптировать под свой стек, дизайн и бизнес-задачу.

06
Реализовать coding agent

После исследования Codex / Claude Code пишет код уже по полученной модели.

07
Сравнить и протестировать

Проверить happy path, ошибки, edge cases и несовпадения. Unknowns не маскировать догадками.

13 / ПРОФИЛЬ

Сильный в сложном. Избыточный в простом.

Сильная сторона

Evidence-first разработка

Требовать доказательства, отмечать неизвестное и строить реализацию по результатам исследования.

Сильная сторона

Закрытое ПО и сложная логика

Обычно не нужен

Простые сайты и UI

Специализированный

14 / РИСКИ

Границы, которые важно видеть заранее

Декомпиляция не равна восстановлению исходника

Псевдокод и найденные связи помогают понять поведение, но это не оригинальный проект автора со всеми именами, комментариями, архитектурными решениями и контекстом.

AI всё ещё может ошибочно интерпретировать evidence

Правильный процесс требует различать наблюдаемое, вывод и неизвестное. Если агент превращает гипотезу в «факт», вы теряете главное преимущество подхода.

Локальный анализ не отменяет политику вашего AI-провайдера

REA указывает, что собственного hosted analysis service у него нет, но coding agent или модель могут иметь отдельные правила обработки данных. Для чувствительных материалов их нужно проверять отдельно.

Право на reverse engineering зависит от контекста

Лицензии, договоры, технические меры защиты и применимое право могут ограничивать допустимые действия. Для учебных и продуктовых задач безопаснее исследовать разрешённые объекты и строить собственную реализацию, не перенося чужой закрытый код, ключи, ассеты или обходы защиты.

15 / PROMPTS

Готовые шаблоны постановки задачи

01 · Сначала исследование, без реализации 
Используя REA, исследуй [конкретную функцию / механику].

Определи:
1. пользовательские состояния;
2. переходы между состояниями;
3. validation и ошибки;
4. keyboard / pointer behavior;
5. edge cases;
6. что подтверждено наблюдением или анализом.

Для каждого вывода поставь метку:
OBSERVED — непосредственно наблюдалось;
INFERRED — вывод из evidence;
UNKNOWN — достоверно не установлено.

Пока ничего не реализуй.
Сначала подготовь research report и перечисли, какие вопросы остались открытыми.
02 · Реализация после исследования 
Возьми утверждённый research report по [механике].

Собери собственную реализацию для нашего проекта:
- без переноса чужого закрытого кода;
- в нашей архитектуре;
- в нашем визуальном стиле;
- только с теми функциями, которые нужны нашей задаче.

Сначала покажи:
1. архитектуру решения;
2. список файлов, которые будут изменены;
3. критерии проверки поведения.

После этого реализуй маленькими этапами и после каждого этапа запускай проверку.
03 · Проверка реализации против evidence
Проверь реализованную механику [название] по нашему research report.

1. Составь таблицу: требование → тест → фактический результат.
2. Проверь happy path, пустые значения, ошибки, крайние случаи и keyboard UX.
3. Сравни наблюдаемое поведение с исходным исследованием.
4. Для неподтверждённых деталей отметь UNKNOWN, а не придумывай эталон.
5. Покажи расхождения по приоритету P0/P1/P2.
6. Ничего не исправляй, пока не покажешь отчёт.

В конце выдай решение: READY / NEEDS FIX / INSUFFICIENT EVIDENCE.

02 / НАСТРОИТЬ

Подключить к агенту

Запустите мастер, выберите агента, проверьте предлагаемые изменения и подтвердите. После настройки перезапустите агента.

npx rea-agents setup
03 / ПРОВЕРИТЬ

Сделать диагностику

После настройки запустите проверку готовности, затем дайте агенту маленький разрешённый объект исследования.

npx -y rea-agents@latest doctor
04 / НЕ ПЕРЕУСЛОЖНЯТЬ

Бинарный анализатор не всегда нужен

Для JavaScript/Electron и некоторых статических сценариев нативный декомпилятор не требуется. Ставьте Ghidra/Hopper/IDA только под конкретную задачу.

REA не появляется в агенте

Убедитесь, что мастер настроил именно используемый агент; перезапустите его. Проверьте диагностику и конфигурацию MCP по официальной инструкции. Не переустанавливайте всё подряд.

Не поддерживается версия Node.js

Проверьте node --version. REA работает не с любым major-релизом. Сверьтесь с таблицей поддерживаемых версий перед повторной установкой.

Нет Ghidra / Hopper / IDA

Для глубокой декомпиляции нативного бинарника нужен соответствующий provider. Для веб-страницы или статического JS часто можно обойтись без него. Проверьте тип цели и требования provider.

Исследование вернуло мало evidence

Сузьте вопрос и проверьте, доступна ли агенту нужная часть программы. Запросите явно ограничения и unknowns; не приравнивайте отсутствие evidence к доказательству отсутствия функции.
